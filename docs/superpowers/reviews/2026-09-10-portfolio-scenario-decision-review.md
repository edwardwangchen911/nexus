**审查基线：** `main@0b1ce31f`

**最终结论：** 通过，可进入实施；不得跳过计划任务或扩大 V1 边界。

## 第一轮审查

**得分：89/100，不通过。**

发现并要求修正：

1. 原始构想只写“最大换手”，没有说明现金腿。现有方案模型只对证券差异除以二，卖出转现金可能被低估一半。
2. 原始构想把集中度笼统描述为总资产占比，但现有诊断 Top1/Top3/HHI 是 security-only 分母，存在跨层口径错配。
3. “Agent 调用情景工具后保存方案”没有说明写入所有者，可能让 Agent 工具产生数据库副作用。
4. Mandate 与系统硬风控边界不够明确，可能出现用户约束放宽系统政策。
5. 两级 `analysis_comparable/execution_eligible` 缺少决策与 Shadow 边界，可能把 partial 分析显示成推荐。
6. 直接替换固定三方案会同时冲击模型、API、数据库和 Shadow，迁移风险过大。

上述问题均已在最终设计中修正：定义现金腿换手、冻结 security-only 口径、采用只读工具加确定性重算落盘、建立三层约束、拆开分析/决策/Shadow/执行，并保留旧三方案并行兼容。

## 第二轮审查

**得分：92/100，不通过。**

第一轮问题修复后，进一步按真实 Web 调用路径复核，发现：

1. 计划只列 Engine API，没有列出 vinext BFF 路由、封闭路径模板、HMAC 规范化和运行时响应校验，页面无法按现有安全架构直接开发。
2. 纯计算返回模型包含 `scenario_id`，但函数签名没有 ID 输入且又禁止 UUID 生成器，合同自相矛盾。
3. 纯计算结果包含 `decision_status`，但该状态依赖尚未产生的 Agent intent，造成层次倒置。
4. 人工选择被描述为追加记录，但迁移设计没有对应表，且与情景不可变约束冲突。
5. 组合级模型调用缺少持久化 Job、POST 202/GET 恢复合同；客户端断流后无法证明不会重复调用模型。

最终稿已增加完整 BFF 文件和测试，拆分 `PortfolioScenarioEvaluation` 与 `FrozenPortfolioScenario`，把 decision readiness 移到 Agent 后置派生，增加不可变 `portfolio_scenario_selections` 表，并补齐 `portfolio.decision` 单次 Job 与持久化状态恢复入口。

## 第三轮审查

**得分：94/100，不通过。**

对计划中的 `Modify/Test` 路径逐项与仓库核对后，发现数个不可直接执行的路径：组件测试实际位于 `tests/unit/optimize`，全局 UI 样式实际为 `app/styles/ui.css`，且计划引用了不存在的 Agent integration/Responses 测试文件。最终稿已改为现有路径，新增测试均明确标为 Create，并将回归目标改为真实存在的 `test_runtime.py`。

## 第四轮审查

**得分：97/100，通过。**

### 现有架构匹配度：15/15

- 复用 `RealAdvisoryPolicy`、`ScenarioEvidence`、`TypedMetric`、现有 Agent 工具注册和数据库幂等模式。
- 没有把逐标的 `AgentResearchRunRecord` 改成 nullable，而是增加组合级运行记录。
- 旧三方案链路不改写，避免一次性大迁移。

### 安全与权限边界：20/20

- Agent schema、工具输入和工具输出均不允许权重与订单。
- Agent 工具只读；应用在哈希校验后重算并持久化。
- 人工选择不启动 Shadow，任何状态都不解锁执行。
- 测试明确核对 Shadow、订单和成交表零变化。

### 数据、时间和财务口径：15/15

- 集中度分母、现金、换手和 Decimal 精度均已显式定义。
- 所有结果绑定快照、诊断、Mandate、估值时间和输入哈希。

### 接口与持久化可实施性：14/15

### 兼容、迁移与回滚：10/10

- downgrade 顺序、不可变记录、页面入口回滚和旧数据保留均已定义。

### 测试与真实验收：14/15

- 扣 1 分：组合级 Agent 持久化是新增子系统，但这是保证审计绑定且不破坏逐标的运行合同所需的最小新增。

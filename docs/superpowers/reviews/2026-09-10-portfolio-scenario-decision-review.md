## 2. 审查过程

### 第一版：完整架构质量 97/100，最小交付质量 91/100，不准直接实施

第一版正确解决了权重权威、现金腿换手、security-only 分母、Agent 只读和执行锁，但把完整目标架构误写成首轮最短闭环。主要问题：

1. 一次新增五类持久化记录，尚无首个真实候选证明其必要性；
2. 同时实现 Engine/BFF、Agent、Job 恢复、人工选择和页面，失败定位面过大；
3. 独立 `PortfolioMandate` CRUD 早于请求级约束的实际使用证据；
4. `decision_ready` 和 Shadow 准入早于分析候选闭环；
5. 十个任务无法在一个低风险、可审阅的首轮切片内完成。

因此原 97 分只代表终局完整性，不能作为全部十个任务的实施准入。

### 第二版：阶段化后 96/100，发现两项边界歧义

收敛为阶段 A 后，审查发现：

1. 同时把 Top1 与 Top3 作为停止目标会让“降低集中度”成为隐含多目标优化；
2. 页面刷新是否可以自动 POST 描述不够明确，可能违反浏览器只读刷新规则。

最终稿已经修复：阶段 A 只以 `single_name_warning` 为停止目标，Top3/HHI 只展示；只有用户明确点击才 POST，页面加载、普通刷新、组合切换均不计算。

### 第三版：98/100，通过

最终稿逐项核对了现有 `what_if.py`、优化 API/BFF、封闭 Engine 路径、组合页和现有测试位置。没有发现阻断性未定义决策。

### Task 2 开工复核：维持 98/100

领域 `PortfolioSnapshot` 保留原币种事实，不能直接跨 USD/HKD 求和。最终稿因此把阶段 A 固定为 `currency:USD`，要求身份权威确认标准美股，排除 `00656.HK` 且禁止隐含 FX；同时把 `available_quantity` 转成确定性减仓下限，并显式传入权威 `diagnostic_input_hash`。这些是完成既定美股只读情景所需的边界修复，不是新功能。

## 3. 最终评分

### 现有架构匹配度：15/15

- 复用 `PortfolioSnapshot`、`PortfolioDiagnosticReport`、`RealAdvisoryPolicy` 和 `TypedMetric`。
- 复用现有 `what-if/evaluate` 的 bounded body、HMAC、幂等声明和 BFF 安全模式。
- 不修改旧三方案模型、正式 producer、Shadow 合同或逐标的 Agent 运行模型。
- 文件路径与仓库当前结构一致。

### 安全、权限和副作用边界：20/20

- 请求无法提交权重、证券 universe、数量、金额或订单。
- 权重只由确定性代码从冻结快照生成。
- Engine 只读业务事实；持久化只复用现有幂等声明和非敏感审计摘要，不新增业务记录。
- 页面加载和刷新不触发计算或任何外部调用。
- 页面没有推荐、选择、Shadow 或执行操作。
- `execution_locked` 恒为 `true`，且 BFF 校验该事实。

### 数据、时间与财务口径：15/15

- security-only Top1/Top3/HHI 的分母明确。
- 现金腿纳入单边换手，避免卖出转现金被低估一半。
- `Decimal`、一个基点步长和舍入归现金均已定义。
- 快照、诊断、`as_of` 和 `diagnostic_input_hash` 完整绑定。
- 估值域固定为 USD，非 USD 资产不混算；标准美股身份与可出售数量都进入硬约束。
- 成本未知明确返回 unknown，不进入执行判断。

### 合同和接口可实施性：15/15

- 请求、约束、仓位、指标和结果模型字段完整且封闭。
- 纯函数签名无数据库、网络、时钟和随机数依赖。
- 只有一对 Engine/BFF POST，错误码和成功状态边界清楚。
- 哈希规范、BFF 回包身份校验和审计最小化已明确。
- 已明确复用诊断组件完成的快照绑定校验，通过可选回调向同页情景区块传递诊断，不重复发起诊断请求。
- 计划给出精确文件、接口、测试和验证命令。

### 范围控制与交付效率：15/15

- 首轮从十个任务收敛为四个独立可审阅任务。
- 无数据库迁移、Agent 生命周期、Mandate CRUD 或 Shadow 子系统。
- Top3/HHI 降为展示指标，避免隐藏的多目标求解器。
- 阶段 A 单独产生可用结果，不依赖阶段 B、C 才能验收。
- 每个后续阶段有明确准入条件，不能顺手扩大范围。

### 测试与真实验收：13/15

- 覆盖合同、算法、API/BFF、组件、浏览器和 fixture 跨层路径。
- 验收检查旧方案/Shadow/order/fill 零增量，并确认不存在 scenario 业务表。
- 真实验收使用正常产品配置，不刷新券商、不调用模型或 Provider。
- 扣 1 分：真实快照可能不是既有优化基线，届时只能确认正确拒绝，不能证明真实候选成功。
- 扣 1 分：按一个基点循环的最坏迭代次数虽有比例上限，但实现时仍需用测试证明边界时间可接受。

### 兼容和回滚：5/5

- 无 schema 迁移、依赖或外部配置变化。
- 旧三方案和历史数据不变。
- 新能力可通过移除单个 UI 区块、一对路由和两个领域模块回滚。

**总分：98/100。**

## 5. 实施准入与停止条件

阶段 A 可以按实施计划从 Task 1 开始，但必须满足：

1. 实施前核对最新 `main` 与当前 worktree 差异，不覆盖现有用户改动；
2. 一个 worktree 只有一个写入者，Task 1 至 Task 4 依序集成；
3. 每个任务先写失败测试，再写最小实现；
4. 真实验收不触发新券商、行情或模型调用；
5. Task 4 完成后停止，不进入阶段 B。

以下任一情况需要停止阶段 A 并重新评审：

- 当前快照无法用现有权威数据计算一致的组合权重；
- 为生成候选必须新增证券、买入、推断 FX 或修改系统阈值；
- 需要数据库迁移才能完成页面展示；
- 现有诊断的集中度实际不是设计确认的 security-only 口径；
- 纯引擎必须依赖实时外部数据或模型。

# Platform 紧凑输出版本实施计划

> 执行方式：本主线在既有隔离工作区实施，按测试先行验证；不新增并行写入者。

**Goal:** 为未来新研究增加版本化紧凑 JSON 生成指导，保留历史字节、严格业务校验和安全收尾。

**Architecture:** 复用现有 PlatformAllocation.units_version 与完整 body 哈希。新版本沿用 v2 schema 和输入计量；三阶段仅追加一段固定任务指令。先提供可离线验证的编译支持，再接不可变根身份、正常生产者与数据库路由；不得仅改变全局默认值激活。

**Tech Stack:** Python、Pydantic、PostgreSQL、pytest。

**Spec:** 已完成并回核的 NEXUS-COMPACT-OUTPUT-DIAGNOSIS-20261105-R1 评审。

## 固定约束

- 三阶段整链输出上限8192、原输入容量/期限/预算/审计门禁不变。
- 紧凑只是生成指导，不新增“有普通格式空白即失败”的接受规则。
- 不清洗/补全原响应，不提前取消，不重试，不切模型，不改旧请求。
- 原v1/v2请求逐字节重建；未决、排队旧身份不得自动升级。
- 已消费的真实研究授权不由本候选恢复；效果只能由后续获准正常事实证明。

## 重点反例

- 旧版本配新规则、新版本缺规则或同链混版本：原冻结绑定必须拒绝。
- 新增指令导致容量超限：沿原界限拒绝，不裁证据。
- 恢复时依赖CURRENT重算旧allocation：必须按落盘版本重建。
- 根请求先于Run排队：根版本须先冻结并传递，不能从部署时间推断。
- 完整结果有正常JSON格式空白：仍按原业务schema接受；incomplete不能变成成功。

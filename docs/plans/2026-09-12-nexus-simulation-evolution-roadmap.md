# NEXUS 自主模拟与策略进化路线图

**状态：** 当前主线最终梳理稿

**核查日期：** 2026-09-12

**适用范围：** Mac 本地、内部模拟优先、实盘关闭

## 一页结论

NEXUS 的最终目标不是持续生成研究页面，而是形成下面这条闭环：

> 真实市场数据 → 固定版本策略作出决策 → 确定性风控 → 模拟订单与成交 →
> 账本和绩效 → 与旧策略及不操作基线比较 → Agent 提出改进 → 样本外验证 →
> 合格后进入下一轮模拟。

项目没有从零开始。行情、研究、确定性策略、内部模拟账户、订单、成交、账本、绩效、
策略研发和晋升模块都已有代码。但是截至本次核查，当前业务库尚未产生策略决策、模拟订单、
模拟成交、策略研发、回测比较或晋升记录。因此准确状态是：

> **基础模块较完整，真实运行闭环尚未开始。**

当前优先级不是继续造系统，而是让现有模块使用正确的数据，先完成一次真实数据驱动的内部
模拟闭环。研究 Shadow 暂停作为独立产品线；其中“不操作基线”的思想以后复用到模拟绩效。

## 迭代了多久，成果为什么看起来不清楚

现有核心迭代记录至少覆盖 2026-09-02 至 2026-09-12，共 10 天。期间完成的真实账户只读、
数据身份、诊断、候选、Agent 解读、风控、模拟账本和进化模块并非无效工作；它们构成后续闭环
的基础。问题是最近把“冻结候选跟踪”扩张成独立研究 Shadow，并持续增加迁移、复权评价版本和
接口，却没有先完成第一笔模拟决策与成交。这部分不能计入核心目标的运行进展。

如果按最终目标而不是代码量衡量：五个阶段中尚未完成第一个运行阶段，目前位于阶段 0。
这不等于只完成了 0%，因为大量基础可以复用；但也不能再说“基本完成，只差开市验收”。

## 用户最终要得到什么

系统应在明确的资金、股票池、频率和风控范围内自主进行内部模拟，不要求用户逐笔批准内部
模拟决策。系统持续记录：

- 为什么买、卖或不交易；
- 订单是否通过风控，是否成交，成交价格和模拟成本；
- 现金、持仓、收益、回撤、换手和风险如何变化；
- 相比保持不动、旧策略和市场基准，操作是否真正改善结果；
- Agent 提出的改进是否通过未来样本验证。

模拟成绩不能自动获得实盘权限。券商模拟写入、实盘和硬风控变更仍是独立授权边界；最终是否
进入实盘由用户决定，实盘订单继续逐笔人工确认。

## 股票数据到底是什么情况

股票数据是存在的：

- Alpaca `all` 复权日线清单 30 份，其中 29 份至少 200 行；
- Alpaca 原始分钟清单 16 份，但当前每份只有 1 行；
- 复星原始日线清单 281 份，其中多数超过 200 行。

此前产生混乱的不是“没有股票数据”，而是两件事：

1. **股票池身份曾被错误复用。** 当前库中的 `us_liquid/us_liquid_v1` 只有一个成员，来源和
   用途写明为本地只读行情展示。它是早期遗留记录，不是正式策略池。后续代码已经把展示池
   改名为 `fosun_local_holdings`，但旧记录仍然保留。
2. **正式策略定义与已落库数据尚未逐项对齐。** 仓库中的固定 `us_liquid_v1` 工程定义包含
   49 个标的。不能用旧的单成员展示记录代替它，也不能用多个历史股票池的并集统计冒充覆盖。

因此下一步不是重新采集所有数据，而是按正式策略池逐项核对：标的身份、连续交易日、原始与
复权数据、可用时间、成交量单位、行业分类和用途资格。已有合格数据直接复用，缺口才补。

## 目前真正的断点

### 1. 策略数据读取尚未接纳真实来源

`strategy/snapshot_reader.py` 当前同时存在两层拒绝：旧 v2 来源政策不授权复权用途；底层读取
又只接受 fixture 的成交量单位。直接把一个布尔值改成 `True` 仍然跑不通，也不安全。

需要解决的是：对已经持久化并可重算的真实日线，明确价格、成交量单位、时点和用途合同，
然后让现有读取器接入；不是再造价格系统。

### 2. 正式策略池还没有合格的冻结输入包

当前没有 rank checkpoint，也没有一份已验证的正式 49 标的输入包。结构化行业记录目前为零，
但项目已有人工审核资料的导入入口；缺的是实际合格输入，不是行业框架。

### 3. 模拟成交窗口尚未形成

现有执行模型需要 1 分钟行情组成精确 5 分钟窗口，并使用成交量、报价和滑点规则。当前零散的
一分钟记录不足以建立合格窗口，因此还不能产生可信模拟成交。

### 4. 成本模型是模拟假设，不是账户真实费用

当前 `execution_model_v1` 使用 1% 成交量参与率、报价/无报价 10/25 bps 滑点，同时佣金和监管费
设为零。这可以作为明确披露的工程假设，但不能冒充真实券商成本，也不能据此判断可实盘。

### 5. 策略进化代码没有真实运行证据

Agent R&D、样本外验证和晋升代码存在，但当前没有一条实际记录。必须先让固定冠军策略形成模拟
基线，再让候选在冻结标准下与它比较，不能先生成改进文字然后宣称发生了进化。

## 立即停止的工作

- 暂停并不合并 `edward/scenario-research-shadow` 上的独立五日研究 Shadow 扩张；
- 暂停 `0058` 评价版本、专用复权评价 API/BFF 和相关页面开发；
- 不新增通用公司行动体系、第二套策略注册、第二套模拟账本或新的规划治理系统；
- 不把人工研究选择作为内部模拟和策略研发的前置条件；
- 不通过放宽来源、伪造空公司行动、改写旧数据或使用未来行情来通过验收。

现有 worktree 和分支先保留，避免丢失可复用实现；是否拆取少量代码，在第一轮闭环完成后再决定。

## 后续迭代顺序

### 阶段 0：确定一次模拟的真实输入

**用户结果：** 页面或报告能够清楚回答“准备运行哪个策略、哪些股票、使用哪些数据和成本假设”。

只完成以下内容：

1. 核验模拟账户和 `baseline_v1` 注册链的完整性；
2. 校验正式 `us_liquid_v1` 定义，拒绝同名展示池；
3. 逐标的生成现有数据覆盖清单，不重新采集已有合格数据；
4. 明确行业、复权日线和分钟成交窗口的实际缺口；
5. 固定第一轮使用的执行模型及其“模拟假设”标签。

**完成标准：** 得到一份可机器校验的冻结输入或准确缺口清单，并能证明不会选中旧展示池。
该阶段不创建策略决策、订单或成交。

### 阶段 1：跑通一次内部模拟

**用户结果：** 现有策略通过正常产品入口完成一次决策、风控和模拟执行，并能从页面/API看到同一事实。

复用 `paper_once forward → admit → advance` 和现有模拟服务。一次完整验收必须覆盖：

- 合理不交易；
- 风控拒绝；
- 至少一笔正常模拟成交；
- 部分成交或数据不足；
- 结果未知后只读对账，不换幂等键重发；
- 账本守恒、无重复成交、执行锁不影响内部模拟事实但仍阻止实盘。

若真实数据只能到达拒绝路径，只报告拒绝路径成立，不能宣布单次模拟闭环完成。

### 阶段 2：持续运行并建立对照

**用户结果：** 同一个版本的策略按固定节奏持续模拟，用户能看到每天发生了什么以及表现差异。

运行频率沿用策略本身的再平衡规则；当前基线是周频判断，不能描述成 Agent 每日自由交易。
每个交易日可更新行情、订单状态、账本和绩效，但只有策略到期时才产生新决策。

主要对照为：

- 同起点、同资金和持仓的“不操作”基线；
- 当前冠军策略；
- 合适的市场基准；
- 真实账户仅作辅助比较，单独处理出入金、人工操作、币种和时间差。

至少展示净收益、最大回撤、换手、风险暴露、模拟成本、成交率和数据缺失率。持续运行的周期和
停止条件在启用调度前单独确认；本路线图不隐含创建定时任务。

### 阶段 3：让 Agent 有证据地改进策略

**用户结果：** Agent 提出一个明确改动，并能说明它为何被接受、拒绝或继续观察。

流程固定为：

1. Agent 只提出候选策略和理由；
2. 确定性代码验证表达式、参数和风险边界；
3. 用历史训练窗口筛选；
4. 用冻结样本外窗口与冠军及基线比较；
5. 进入并行内部模拟；
6. 只有预先约定的收益、回撤、成本、稳定性和数据完整性门槛全部通过，才切换下一代冠军；
7. 不通过则保留原冠军，并记录失败原因。

不能根据结果临时修改指标或窗口；不能用同一段数据既优化又验收；短期盈利不等于有效进化。

### 阶段 4：接券商模拟盘验证执行差异

**用户结果：** 同一策略在券商模拟环境中验证订单生命周期、回报、对账和恢复行为。

这一阶段只验证外部执行可靠性，不替代策略验证。进入前必须证明模拟账户无法触及实盘，并明确
账户、资金、订单范围、限额、停止条件及回滚；这是外部写入，需要单独授权。

### 阶段 5：由用户决定是否尝试实盘

只有内部模拟、样本外验证、券商模拟、费用和异常恢复均积累足够证据后，才向用户提交是否进入
实盘的评估。系统无权自行解锁，实盘订单仍逐笔确认。

## 下一份技术方案的唯一范围

下一份技术方案只覆盖“阶段 0 + 阶段 1 的最小必要部分”，不得提前实现持续调度或 Agent 进化。
方案需要精确回答：

- 如何识别正式 `us_liquid_v1` 并拒绝旧展示池；
- 正式成员中哪些现有 raw/all 日线可用，缺口如何输出；
- 真实来源成交量单位如何获得可信合同；无法证明时如何拒绝；
- 现有行业导入是否满足策略输入，缺哪些标的；
- 如何由正常入口形成一个合格 5 分钟模拟成交窗口；
- 需要修改哪些现有文件，为什么每一处不可省略；
- 如何测试正常成交、拒绝、部分成交、幂等、回滚和零实盘订单；
- 如何在页面/API展示同一决策、订单、成交、账本和模拟成本假设。

默认限制：不新增数据库表，不新增依赖，不新建独立页面，不复用研究 Shadow 作为执行前置。
若现有 schema 确实无法表达必要事实，必须先以具体失败案例证明，再单独审查最小迁移。

## 开发准入与汇报方式

技术方案进入开发前必须同时满足：

- 目标确实推进一次模拟闭环；
- 数据来源及用途在正常入口上可达；
- 没有更小的现有实现可复用；
- 资金、时间、幂等、成本和执行边界明确；
- 验收覆盖真实数据路径，而非只有 fixture；
- 审查达到 95 分以上且没有未解决的关键问题。

评分只是最后的质量检查，不能替代来源可达性。每轮完成一个用户可见闭环后停止，不自动扩展相邻功能。

后续进度只用五项汇报：**可用结果、真实运行证据、当前阻塞、下一步、需要用户决定的事项。**
不再用迁移数量、代码行数、测试数量或“任务进行中”代替项目进度。

## 当前准确结论

截至 2026-09-12：

- 研究和基础模块已经积累较多，不应推倒重来；
- 内部模拟账户已初始化，但自主模拟尚未开始；
- 股票数据存在，核心问题是正式股票池、数据用途与消费入口尚未对齐；
- 研究 Shadow 独立扩张偏离了当前优先级，已暂停；
- 下一步是为阶段 0/1 写精确技术方案，审查通过后实施；
- 现在不是“只差一次开市验收”，也不是“整个系统需要重写”。

按最终目标衡量，项目处于**模拟闭环启动前**：工程基础明显超过原型，但有效运行证据仍接近起点。
只有出现第一条可追溯策略决策、模拟成交和账本结果后，才进入真正的策略验证阶段。

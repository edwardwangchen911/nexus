# 常驻研究服务安全恢复实施计划

> 实施方式：主线在既有隔离工作区串行写入；独立只读审查辅助。按 TDD 先验证失败，再最小实施。当前设计评审 marker：`nexus-resident-safe-recovery-design-20261026-01`，已收到条件式设计批准；实现终审尚未完成。

**目标：** 已启用的常驻服务退出或登录后，可在安全条件满足时自主恢复；未知业务保持隔离和可诊断，不重放研究、不依赖 Codex 续办。

**架构：** 沿用 macOS 服务管理入口与每用户控制锁，增加一次性、有界的本地恢复检查。业务宿主保持原生命周期锁；恢复子进程取得锁后，在首次心跳和监控前再检查业务安全条件。监督检查不得发送模型、来源或通知请求。

**技术：** Python 3.12、macOS launchd、现有 PostgreSQL 只读守卫；不新增依赖或迁移。设计及批准范围由本文件和同 marker 的 Chat 评审共同约束；设计已条件批准，下述实现进度不代表已发布。

## 固定边界

- `execution_locked=true`；原账户、模型、日槽、预算、审计、时效与价格门禁原样。

- 已接受历史未知沿原精确封存/接受资格判断，不把未知费用改已知，也不新增永久阻断。
- 缺退出证明、未知/在途、配置不符、DB不可用仅诊断，不能自动ack、清锁、清预算或重放。
- 运行状态与业务状态分离；只读监督检查不调用业务heartbeat/monitor。

## 评审关注与回归

1. 外部预检与首次heartbeat之间新占用：取得进程锁后重验；未知时来源、模型、业务写入均零。
2. 旧PID重用、子进程迟退、同机双启动、重启后旧heartbeat：无充分证明不启动，最多一宿主。
3. stop/维护与恢复竞争、退出75、非零/丢失退出回执：停用优先，不自动清除原退出证据。
4. 已接受未知、未消费有效lease、已消费未来lease、旧日claim：真实PG证明沿原完整资格，不新增宽松或过度阻断。
5. 依赖反复失败与时钟回退、状态文件损坏：有界退避、固定安全原因、停用/限额跨进程持久化。
